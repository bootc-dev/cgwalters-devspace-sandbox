# boot-2402: finalize through a detached /boot dirfd (spike)

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.
The issue asks for `DESIGN.md`, but the hand-back refuses any file with that name, so the design notes are here instead.

## Recommendation

Complement PR 3690. Don't replace it. Land PR 3690 as it is: it fixes the reported bug (/boot on the root filesystem, with gpt-auto's ESP automount stacked on it), and the dirfd variant adds nothing for that layout. Its approach for that layout is the same: open `/sysroot/boot`. Keep the detached-mount idea for separate /boot as a follow-up. It isn't needed to fix 2402, and it has a blocking bug, described below. On separate /boot, stock ostree finalized correctly in every scenario we tested.

## Prototype

`patches/` is `git format-patch` output against ostreedev/ostree main a4cb6781. Patches 0001-0004 are PR 3690 as it stands. Patches 0005-0006 are the spike:

- 0005 adds `src/libostree/ostree-bootfs.c`. On a booted system with a separate `/boot`, it opens the boot filesystem as a detached mount and never touches the `/boot` path. It first tries `open_tree(OPEN_TREE_CLONE)` of the `/boot` mount, opened `O_PATH` so an automount is not triggered. If that mount isn't there, it uses `fsopen`/`fsconfig`/`fsmount` on the fstab device or `/dev/disk/by-designator/xbootldr`. It falls back to the path when the process is unprivileged or the new mount API is missing. To make it writable, it uses `fspick` plus a reconfigure to `rw`, not a remount of `/boot`.
- 0006 changes the finalize units from `RequiresMountsFor=/boot` to `WantsMountsFor=/boot`. An expiring automount then no longer stops the unit, which would finalize early. This makes the `/boot` hold from PR 3690 unnecessary.

The branch was not pushed to cgwalters-forge/ostree. Nothing went upstream. The bootc composefs backend was not prototyped. A survey found it already works through dirfds, apart from `get_boot_dir_for_grub`/`hold_boot` in `store/mod.rs` and `finalize.rs`, which open `/boot` by path.

## Test evidence

`harness/` builds ostree (`build-ostree.sh`), overlays it on fedora-bootc:44 (`build-images.sh`), and installs disks (`install-all.sh`). `run-matrix.sh` then boots each disk with SeaBIOS, so gpt-auto automounts the unused ESP. It waits out any automount, stages a deployment with a marker karg, waits again, reboots, and checks that the marker booted. The VMs ran on the runner's own KVM: nested KVM inside the builder VM was too slow, with about 400 s from power-on to the initrd. Per-scenario logs are in `results/`.

| scenario | stock 2026.4 | PR 3690 | dirfd (0001-0006) |
|---|---|---|---|
| bootc, /boot on root (gpt-auto ESP automount) | **LOST**: `Remounting /boot read-write: Invalid argument` | booted | booted |
| bootc, separate ext4 /boot (`auto ro` in fstab) | booted | booted | booted |
| same, with `x-systemd.automount,x-systemd.idle-timeout=60` | booted | booted | booted, but `boot.mount` failed twice (below) |
| same, `umount /boot` after staging | booted (umount refused: busy) | booted (umount refused: busy) | booted (umount succeeded) |

In every row `bootc status`, `ostree admin status`, `ostree admin kargs edit-in-place` and `ostree admin deploy --stage` returned 0. The new BLS entries were labelled `boot_t`, and the previous boot logged no AVC denials. One exception: on stock with /boot on root, the karg from `edit-in-place` was missing from the entries after the failed finalize. `results/bootc-stock-onroot.txt` shows that run.

This run fixed two harness bugs that kept the earlier matrix from running everything. `run-matrix.sh` emitted a trailing blank for scenarios without a mode, which `xargs -L` treats as a continuation, so lines were joined and scenarios silently skipped. The `automount` step only rewrote a `defaults` option, which bootc's `auto ro` fstab line doesn't have, so it did nothing on separate /boot.

Not run: Silverblue with /boot on root, and ostree main. The pilot in the previous run had already shown that main behaves like stock. Their disks were installed, but the nested VMs were too slow, and copying the Silverblue disks out was dropped for time. The stock-vs-PR 3690 result on /boot on root is the same bug path Silverblue takes on a BIOS boot, but it has not been checked on Silverblue itself.

## Comparison

**Systemd's view of /boot.** This is where the dirfd prototype is wrong as written. When nothing is mounted at /boot (an expired automount, or after `umount`), 0005 creates a new superblock with `fsmount`, read-write. finalize-staged holds that mount from staging until shutdown. A later automount trigger then runs `mount -o ro` on the same device. The kernel refuses to attach a read-only mount to a read-write superblock, so `boot.mount` fails with status 32. In `results/bootc-dirfd-sepboot-automount.txt` that happened at 122 s and 161 s: `/boot` was unusable for everything else on the system until reboot. A fix would create the superblock read-only and flip it to `rw` with `fspick` only for the duration of a write, as remounting does today. That is still a filesystem mounted behind systemd's back, which it can't see in `/proc/self/mountinfo` and won't fsck. PR 3690 keeps systemd in charge: the hold unit keeps /boot busy. That is also why `umount /boot` was refused on stock and PR 3690, and why their automount never expired after staging.

**Fsync and durability.** Both write the BLS entries and the bootversion swap through `boot_fd` with `*at()` calls, and both `syncfs`/`FIFREEZE` that fd. A clone of an existing mount shares its superblock, so durability is unchanged. A superblock created by `fsmount` is flushed when the last fd closes. The first dirfd revision failed (`ioctl(FIFREEZE): Bad file descriptor`) because mount fds are `O_PATH`. 0005 now hands out `openat(mnt, ".")`, which worked in every scenario above.

**SELinux.** No difference in these runs: `boot_t` entries, no AVCs. The detached mount's new files get the same type transitions as the path. But `fsmount` applies none of the fstab options, so a `/boot` that relies on `context=` (vfat XBOOTLDR is the likely case) would be labelled differently from systemd's mount. PR 3690 inherits whatever systemd mounted.

**Older kernels.** 0005 needs `open_tree`/`fsmount`/`fspick` (5.2) and `mount_setattr` (5.12). It falls back to the `/boot` path on `ENOSYS`, which is PR 3690's behaviour. So RHEL 9 (5.14) gets the new path, and older kernels lose nothing. PR 3690 needs nothing new.

**Interactive `ostree admin`.** With PR 3690, root reads /boot on root through `/sysroot/boot`, so `ostree admin status` and `kargs edit-in-place` work after the ESP automount expired, also from another mount namespace. With a separate /boot, they trigger the automount as before. With 0005, root never triggers it and gets a private mount instead, which then collides with systemd as described above. Unprivileged callers use the path in both.

**Bootloader backends.** Neither approach helps backends that shell out with paths (`grub2-mkconfig`, zipl, aboot, u-boot): they still need `/boot` mounted. That is the main reason a pure "never touch /boot" design can't be complete without reworking those backends.
