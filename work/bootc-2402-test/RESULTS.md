# bootc#2402 reproducer: results

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

`bootc-tmt-test.patch` applies to bootc main at c3be524. It adds
`tmt/tests/booted/test-boot-automount-idle-update-timer.nu` (test 67) and its
generated fmf. The test has three boots:

1. It checks that `/boot` is gpt-auto's `boot.automount` (it is, stacked on
   ostree's bind `boot.mount`) and sets `TimeoutIdleSec=10s` with a drop-in.
   It then switches to a local v1 image, so the host tracks containers-storage.
2. It builds v2 under the same tag but stages nothing. It waits until the only
   mount at `/boot` is the autofs one, then fires
   `bootc-fetch-apply-updates.timer` through a runtime drop-in (`OnActiveSec=1s`,
   no randomized delay). If the service fails without rebooting, the
   `tmt-reboot -c` command reboots anyway.
3. It prints the previous boot's journal for the updater, finalize and `/boot`
   units, and asserts that v2 booted.

Both runs used `just build` with `BOOTC_base=quay.io/fedora/fedora-bootc:44`
(bootc 1.17.4 from c3be524, systemd 259.10), then
`cargo xtask run-tmt <image> boot-automount-idle-update-timer` with bcvk
0.22.0 (libvirt session, UEFI).

## bootc main, ostree 2026.4-1.fc44: fails

The timer starts the service. bootc's access to `/boot` triggers the
automount, and v2 stages. At shutdown, systemd stops `boot.automount`, which
takes the stacked bind mount down with it before `ostree-finalize-staged`
runs:

```
fedora systemd[1]: Unset automount boot.automount - EFI System Partition Automount.
fedora systemd[1]: Stopping ostree-finalize-staged.service - OSTree Finalize Staged Deployment...
fedora systemd[1]: boot.mount: Deactivated successfully.
fedora ostree[2421]: error: Remounting /boot read-write: Invalid argument
fedora systemd[1]: ostree-finalize-staged.service: Failed with result 'exit-code'.
```

v1 boots again, and the test fails on `the update applied by the timer should
have booted` (marker `v1`, expected `v2`). The failure message differs from
the `opendir(boot): Operation not permitted` the issue reports. Here finalize
finds an empty `/boot` directory, not a dead autofs mount, but the outcome is
the same: the update is lost.

## ostree 2026.6.13.g3c3bd130 (ostreedev/ostree#3690): passes

`Containerfile.ostree-fix` builds RPMs from `bot/boot-finalize-2402` of
cgwalters-forge/ostree and layers `ostree` and `ostree-libs` onto the same
`localhost/bootc`. The shutdown sequence is identical, but finalize now works
through `/sysroot/boot`:

```
fedora systemd[1]: boot.mount: Deactivated successfully.
fedora ostree[2427]: Writing the boot filesystem via /sysroot/boot; Remounting /boot read-write: Invalid argument
fedora ostree[2427]: Finalizing staged deployment
fedora ostree[2427]: Finalized deployment
fedora systemd[1]: ostree-finalize-staged.service: Deactivated successfully.
```

v2 boots and the test passes (`total: 1 test passed`).

## Not covered

I did not run a control without the idle-out. `boot.mount` is stacked on the
autofs mount from early boot either way, so it is unclear whether the idle
step is required, or whether the existing upgrade tests escape the bug for
another reason. They may simply not run on a Fedora 44 base with ostree
2026.3 or newer. Only the ostree backend with `/boot` on the root partition
was tested.

The sandbox had no `virtiofsd` or C toolchain, so these runs set
`VIRTIOFSD_BIN` to a virtiofsd from the CentOS Stream 10 RPM, placed under
`/var/tmp`, and linked the xtask build scripts with `zig cc`. Neither affects
the guest.
