## Not verified

- With /boot on the physical root, the path-based bootloader backends
  (grub2-mkconfig, syslinux, uboot, zipl, aboot) would now see a read-only
  /boot, because nothing remounts it. Per the review, those systems use a
  separate /boot. No such system was tested.
- The `--hold` branch that leaves a real ESP at /boot unheld wasn't exercised:
  in these VMs, /boot is always ostree's bind mount.
- Only Fedora 44 (kernel 7.2, systemd 259) was tested, not CentOS Stream 10.
- PR 41's bootc tmt evidence covers one run per image with /boot on the root
  partition, not a separate /boot or a real ESP at /boot.

## Continuation review

One adversarial review pass of the complete PR diff left no classified
blockers, two important findings and one nit open. The patch series was not
changed in this continuation:

- **Important, patch 3:56–60:** path-based backends can still write through
  the read-only /boot bind mount. A separate /boot is an assumption from the
  upstream review, not a restriction enforced by backend selection; the
  successful static-BLS VM runs do not cover this case.
- **Important, patch 2:259–262:** releasing a real ESP descriptor does not
  remove `RequiresMountsFor=/boot` from the finalization service. Automount
  expiration could therefore stop it and finalize early. That layout needs
  lifecycle testing beyond the bind-mount case tested here.
- **Nit, `REVIEW-REPLIES.md:17–19`:** the code still opens /boot
  unconditionally, then decides whether to retain the extra descriptor.
  “Only retains an additional descriptor when…” would be more precise than
  the draft reply's “no longer opens /boot unconditionally”.
