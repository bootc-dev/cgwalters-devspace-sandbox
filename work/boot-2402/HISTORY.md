## The failure to explain

There are two different objects named `/boot`: the boot directory on the
physical root, and its presentation inside an ostree deployment. A systemd
automount can control the latter without owning the underlying boot storage.
[ostree PR 3690](https://github.com/ostreedev/ostree/pull/3690) proposes using
the boot filesystem's file descriptor rather than that presentation path:
for root-hosted boot files, use `/sysroot/boot` and make `/sysroot` writable;
remount `/boot` only for a separate filesystem. The PR is open, not merged,
as checked on 2026-11-11.

The existing matrix's Fedora 45 `stock/root` idle and no-idle rows isolate
the failure; `pr3690/root` rows record the repair. Stream 9's `root-fstab-esp`
BIOS row is an important counterexample to treating every systemd version
alike: an ESP fstab entry does **not** suppress its `/boot` automount.
See [matrix](RESULTS.md#matrix) and [Stream rows](RESULTS.md#rhel-exposure-runs-45-2026-11-11-stream-measurements),
not a new claim that these tests cover all releases.

## Who chooses where boot files live?

“On physical root” means `/sysroot/boot` contains the boot files, not just an
empty mount-point directory. Do not infer the layout from the container tag
or from absence of fstab: callers can supply storage, and CoreOS has its own
mount generator. The sources below describe the ostree/GRUB paths, not all
composefs-native or UKI variants.

Some earlier installer boundaries are documented even where the first release
is unknown. Anaconda already requested a separate `/boot` in its
[May 2010 platform code](https://github.com/rhinstaller/anaconda/blob/78421d4ed23ad58b021c4d9d1bae690b99c167fe/pyanaconda/platform.py#L166-L169),
before [RPMOSTreePayload arrived in May 2014](https://github.com/rhinstaller/anaconda/commit/131cbcec9c113dd5f66d14d440297d50b2900e01).
bootc-image-builder already had separate boot storage when
[`711f39bb`](https://github.com/osbuild/bootc-image-builder/commit/711f39bb12427992936e4f827aea611a4d027050)
made it read-only in February 2024 to protect it from non-ostree package tools.
Importantly, its April 2025
[`8bd5b396`](https://github.com/osbuild/bootc-image-builder/commit/8bd5b3962f2dc87d7b9ce0f5625af7a88b05f925)
dependency update switched bootc disk images to **mount units instead of
fstab**, adopting [images' policy change](https://github.com/osbuild/images/commit/43f1a3251aa37617334bfca7ecb742e86b821449).
That remains the [current default](https://github.com/osbuild/image-builder/blob/0c4d9b8d2e041faf30359634ac21591c7d0384fb/pkg/image/bootc_disk.go#L35-L43).
CoreOS's [September 2019 generator introduction](https://github.com/coreos/fedora-coreos-config/commit/418a48ff8cd0f029ea2b18410e6a2f9fa01bf09e)
replaced existing mount units for separate boot and ESP filesystems.
coreos-installer [copies the disk image](https://github.com/coreos/coreos-installer/blob/9534bacaac10af548b322c17da91bb35efcf0d69/src/install.rs#L380-L415),
rather than applying bootc's `to-disk` partitioning defaults.

CoreOS history also explains why “no ESP fstab entry” is not negligence:
[`33a7393a`](https://github.com/coreos/fedora-coreos-config/commit/33a7393a515c6be8cc89aa1fa3e358033363faac)
stopped permanently mounting `/boot/efi` because RAID systems have multiple
ESPs and no canonical one ([tracker 694](https://github.com/coreos/fedora-coreos-tracker/issues/694)).
[`1de21ffa`](https://github.com/coreos/fedora-coreos-config/commit/1de21ffa98bb22995e5b059501e1955bf52b562c),
merged January 2021, made `/boot` read-only to prevent accidental administrator
or configuration-management writes; controlled tools should remount privately.

## Why ostree has a bind mount and remount code

These are different historical changes, not a single decision to make a
read-only bind mount:

| Change | Reason recorded at the time |
|---|---|
| 2015, [`598530da`](https://github.com/ostreedev/ostree/commit/598530daf45a8bcb3be171732569b8aad0f4345d), in v2015.10 | `ostree-prepare-root` binds the physical `boot` directory into the deployment when `boot/loader` is a symlink. The runtime expects bootloader configuration at `/boot`. The original bind was **not explicitly read-only**. See also [GNOME bug 756267](https://bugzilla.gnome.org/show_bug.cgi?id=756267). |
| 2016, [`8894bb39`](https://github.com/ostreedev/ostree/commit/8894bb39498267f4ae06badc7aa54c4eb4bb7f73) | Support an already-read-only `/boot`: temporarily remount writable for deployment, then restore read-only. Protect against accidental writes such as `rpm -Uvh kernel.rpm`, whose kernel packaging does not understand ostree. Initially uses libmount to distinguish mount points. |
| [PR 1767](https://github.com/ostreedev/ostree/pull/1767), [`5af403be`](https://github.com/ostreedev/ostree/commit/5af403be0cc64df50ad21cef05f3268ead256d6d) (authored 2018, merged 2019) | Opt-in `sysroot.readonly`: conceptually `/sysroot` and mostly `/boot` should only be written through libostree. Keep `/etc` and `/var` writable; add a mount-namespace API so library clients can remount privately. Closes [1265](https://github.com/ostreedev/ostree/issues/1265). |
| 2021, [`9a526bba`](https://github.com/ostreedev/ostree/commit/9a526bbaa5ad6a75e3b0d8052d93934df3e7a20f) | `_ostree_sysroot_ensure_writable` must handle writable `/sysroot` with read-only `/boot`, exposed by [FCOS PR 659](https://github.com/coreos/fedora-coreos-config/pull/659). Remount both when necessary, reopen descriptors, remove the older non-namespace remount path. |
| 2021, [`c553b5c6`](https://github.com/ostreedev/ostree/commit/c553b5c69a9112d6e74919e4eab60a55b07feece) | Move read-only sysroot setup into initramfs to close races ([2115](https://github.com/ostreedev/ostree/issues/2115)). This does not make every existing bind read-only: [3365](https://github.com/ostreedev/ostree/issues/3365) later describes the early `/boot` bind remaining writable, and `ST_RDONLY` being an inadequate mount-point test. |
| 2022, [`f3db79e7`](https://github.com/ostreedev/ostree/commit/f3db79e7fa8d469e539b60ceb7e3d790747e530f), [PR 2544](https://github.com/ostreedev/ostree/pull/2544) | Keep `/boot` open with `finalize-staged --hold` in a **separate service**, in the host mount namespace. Otherwise an idle expiry stops the finalize service and finalizes prematurely; the holder must outlive `ExecStop`. Fixes [2543](https://github.com/ostreedev/ostree/issues/2543), citing [RH bug 2056090](https://bugzilla.redhat.com/show_bug.cgi?id=2056090) for autofs/mount-namespace behavior. |
| 2026, [`a88e66ea`](https://github.com/ostreedev/ostree/commit/a88e66eaf86a3c7b0060073757c02245196f759d), [PR 3571](https://github.com/ostreedev/ostree/pull/3571) | Move the systemd-case bind from prepare-root to generated `boot.mount`, with `DefaultDependencies=no`, because soft reboot does not rerun initramfs. Bind from the now-read-only physical root; retain the static/non-systemd prepare-root path. Fixes [RHEL-154075](https://issues.redhat.com/browse/RHEL-154075). |
| 2026, [`62109dca`](https://github.com/ostreedev/ostree/commit/62109dca5f6dcf10583dab47fc0424513baa59ac), v2026.3 | Publish `/run/systemd/volatile-root` for composefs so systemd can discover the real disk behind overlayfs. Intended to restore ESP discovery, `bootctl` and boot counting; references [systemd 35017](https://github.com/systemd/systemd/issues/35017). This exposes the automount collision, rather than introducing systemd's old idle timeout. |
| 2026, [`09450fcd`](https://github.com/ostreedev/ostree/commit/09450fcd7762c5fab1f58c976567062f1c408f3d), [PR 3654](https://github.com/ostreedev/ostree/pull/3654), v2026.5 | Respect an explicit `/boot` fstab entry. Competing generators could fail with `EEXIST` and omit `var.mount`; this is necessary before recommending an fstab bind as a universal installer workaround. |

The generated `boot.mount` and `boot.automount` are **separate unit names**.
Ostree's normal-generator `boot.mount` wins over gpt-auto's late-generator
mount, but does not displace the automount. Thus a unit described as “EFI
System Partition Automount” can drive ostree's bind instead of mounting the
ESP. Sources: [ostree generator commit](https://github.com/ostreedev/ostree/commit/a88e66eaf86a3c7b0060073757c02245196f759d),
[v239 late output argument](https://github.com/systemd/systemd/blob/v239/src/gpt-auto-generator/gpt-auto-generator.c#L680-L690),
and [recorded generated-unit evidence](RESULTS.md#evidence).

## Synthesis and durable fixes

**3690 addresses the right abstraction boundary:** boot storage must not be
confused with a transient mount at the deployment's `/boot`. Its
[`f123c472`](https://github.com/ostreedev/ostree/commit/f123c4725c54f8249e54d442f5dceb97740e90c0)
opens root-hosted boot storage at `/sysroot/boot` and routes bootversion,
loader-link and cleanup operations through `boot_fd`.
[`960570df`](https://github.com/ostreedev/ostree/commit/960570dfbc2e9fe87c0b115483083f9d710fe66e)
then needs only the sysroot remount for that case, preserving the separate
filesystem remount path. It does not disable another project's ESP discovery.
The holder additionally opens public `/boot` only when its device/inode
matches ostree's bind, preventing premature finalization without pinning an
unrelated real ESP ([review resolution](https://github.com/ostreedev/ostree/pull/3690#discussion_r4498063087)).
The strongest existing evidence is Fedora 44/45 `pr3690/root`, Stream 10
`pr3690/root` BIOS, and [Stream 9's three PR rows](RESULTS.md#run-5-pr-55-continuation--stream-9-pr-3690).
Silverblue-with-PR is explicitly **not** validated in that record.

**Installers should also express mount ownership.** Recommendation, not an
implemented change here: keep a real separate `/boot` mount in fstab when
that filesystem exists; for root-hosted boot files, evaluate an explicit
`/sysroot/boot` → `/boot` bind entry with correct sysroot ordering and
read-only policy. Account for ostree's fstab collision fix in v2026.5 before
backporting this policy ([3654](https://github.com/ostreedev/ostree/pull/3654)).
On systemd v256+, an ESP entry under `/boot/efi` also suppresses gpt-auto's
loader mounts, but it is not a portable substitute for `/boot` ownership on
252. A unit named `boot.mount` alone is not enough: that is already the
collision shown in RESULTS. Preserve intentional automounts on systems whose
actual boot storage is an ESP/XBOOTLDR rather than blindly masking them.

**Do not prescribe `x-systemd.automount=no`.** In v262,
[fstab-generator](https://github.com/systemd/systemd/blob/v262/src/fstab-generator/fstab-generator.c#L864-L875)
tests the option's presence; [fstab-util](https://github.com/systemd/systemd/blob/v262/src/shared/fstab-util.c#L231-L361)
accepts a matching name followed by `=` without parsing its boolean value.
Consequently `=no` still requests an automount. Use an ordinary mount entry
without `x-systemd.automount`; distinguish suppressing gpt-auto via fstab
from asking fstab-generator to create another automount.

**The `/efi` direction needs a policy change, not just `mkdir /efi`.** The
3664 review's suggestion is sensible separation of bootloader storage from
ostree's boot directory, but current v254+ selection prefers available
`/boot`; the Fedora `root-efidir` rows fail while the older Stream 9 BIOS
`root-efidir` row moves the ESP successfully. Any new systemd preference must
retain compatibility for real ESP-at-`/boot` users (sources and rows above).

**Residual risks:** 3690 retains the historic `boot/loader` symlink heuristic;
[its review](https://github.com/ostreedev/ostree/pull/3690#discussion_r4521422499)
still questions that identity test. Path-based bootloader backends and
custom layouts need explicit coverage; the PR's remount commit assumes those
backends use separate boot storage. Invalid/missing separate mounts are not
repaired by fd access (RESULTS `part-nofstab`/`xbootldr-nofstab`). UEFI is not
a permanent exemption: loading GRUB BLI, selecting systemd-boot, or booting
a systemd-stub UKI can supply `LoaderDevicePartUUID`. The
[el10 source/payload audit](RESULTS.md#run-5-el10-boot-chain-audit) found BLI
support and a mkconfig helper, but no active writer in bootupd's static
configuration; BLS support alone is not BLI. Future systemd discovery,
filesystem probing and mount-order changes must be checked against the
installed configuration, not assumed safe from a major-version number.

## Research limits and continuation

The key causal commits and upstream release boundaries are verified; the
installer table intentionally separates exact bootc history from current
Anaconda/image-builder/CoreOS source snapshots. Still missing are the first
separate-boot introduction releases for Anaconda, bootc-image-builder and
each FCOS/RHCOS image architecture, and a complete RHEL minor/z-stream
backport inventory. Do not promote those snapshots into “since release X”
claims. Continue with historical manifests/kickstarts and matching shipped
SRPMs; no additional VM evidence is needed for that research. RH bug links
above are corroborated by public commit messages, not independently audited
private tracker discussions.
