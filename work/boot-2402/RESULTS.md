## Answer to the fstab question, from the systemd source (v257 to v262)

- gpt-auto-generator's `process_loader_partitions()` calls `fstab_has_mount_point_prefix_strv(STRV_MAKE("/boot", "/efi"))` (v262 gpt-auto-generator.c:1089, v259:1015, v257:730). Any fstab entry at or under `/boot` or `/efi`, including `/boot/efi` on its own, suppresses both the ESP and XBOOTLDR automounts. So **yes, a `/boot` (or `/boot/efi`) fstab entry stops gpt-auto from creating `boot.automount`.**
- `add_partition_esp` (v262:671-700) puts the ESP at `/boot` whenever there is no XBOOTLDR and `/boot` is an empty, unmounted directory. An ostree deployment's `/boot` is exactly that. The ESP goes to `/efi` only if `/boot` is busy, so **adding `/efi` to the image does not help**.
- Without a `LoaderDevicePartUUID` EFI variable, gpt-auto creates nothing on UEFI. On BIOS boots it skips that check (v262:1098, v259:1023, v257:738), so an ESP or XBOOTLDR that nothing uses still gets automounted. CentOS Stream 10's grub doesn't set the variable, which is why CentOS only shows the automount on BIOS.
- The idle timeout is hardcoded at 120 s (`LOADER_PARTITION_IDLE_USEC`). It can't be configured.
- gpt-auto writes to `generator.late`, so for `/boot` on root, ostree's `boot.mount` (written to `generator`) wins the unit name. Nothing competes with gpt-auto's `boot.automount`, which then ends up driving ostree's bind mount.
- XBOOTLDR mount options (`partition_pick_mount_options()`, v262 dissect-image.c:2385, v257:1894): "ESP/XBOOTLDR is almost certainly VFAT, hence if we don't know assume it is". If no fstype was probed, the generator adds FAT-only options (`umask=0077` in v257, `fmask=0177,dmask=0077` in v262).
- ostree's generator skips its own `boot.mount` for an exact `/boot` fstab entry starting with v2026.5. With 2026.4 that doesn't matter for a separate `/boot`, because that path never generates the bind mount.
- ostree 62109dca (v2026.3) makes gpt-auto work on composefs roots. That change is what exposed this bug.

## What this shows

- **The bug reproduces** on a stock `bootc install to-disk` of fedora-bootc:45 and :44 (UEFI and BIOS), on CentOS Stream 10 on BIOS, and on Silverblue with `/boot` on root and no ESP line in fstab. Staging after the idle-out works, because bootc 1.17.1 includes bootc#2411, but finalize at shutdown fails and the update is silently dropped. The runs without an idle wait succeed.
- **It needs `/boot` to be ostree's read-only bind mount under gpt-auto's automount.** When the automount covers a real XBOOTLDR partition (CentOS, BIOS), stock ostree survives the idle-out and finalizes fine.
- **ostree PR 3690 fixes every `/boot`-on-root layout tested**, on UEFI and BIOS, for Fedora 44, Fedora 45 and CentOS Stream 10.
- **An fstab entry for `/boot` or `/boot/efi` prevents the automount**, as the source says, and every such layout survived. Default Silverblue (Anaconda) has both entries, so it is not affected.
- Separate-`/boot` layouts without an fstab entry are broken whatever the ostree version. With a generic Linux partition type, or XBOOTLDR on UEFI without `LoaderDevicePartUUID`, nothing mounts `/boot`. With an ext4 XBOOTLDR on Fedora 45, the system doesn't boot at all.

### UEFI boot-chain source check: incomplete, not a negative finding

The current el10 GRUB dist-git **already has a BLI-loading patch**. This is
important: absence of the variable in these VMs is not proof of absence of
GRUB support. Examined:

```console
git clone --depth=1 --branch c10s https://gitlab.com/redhat/centos-stream/rpms/grub2.git /tmp/opencode/grub2-c10s
git -C /tmp/opencode/grub2-c10s log -1 --format='%H %s'
git -C /tmp/opencode/grub2-c10s grep -n -i -E 'LoaderDevicePartUUID|LoaderInfo|boot.?loader interface|bli\.mod|insmod bli'
```

HEAD was `55e23b984b208887a686f5287c0834e7944e0494`, spec Version 2.12,
Release 58. `0275-load-EFI-commands-inside-test-expressions.patch`, dated
2024-09-04, changes `util/grub.d/25_bli.in` from `insmod bli` to:

```text
if [ ! insmod bli ]; then
        echo "bli module not available"
fi
```

The spec/changelog search shows BLS entries, including skipping BLS updates
on ostree; BLS snippet support is not itself proof of setting the EFI
variable. The upstream RH GRUB mirror's
[`grub-core/commands/bli.c`](https://github.com/rhboot/grub2/blob/master/grub-core/commands/bli.c)
calls `set_loader_device_part_uuid()` from `GRUB_MOD_INIT(bli)` and writes
`LoaderDevicePartUUID`. That moving-branch source is context, not a verified
match to the shipped binary. Still to check: the el10 source tarball and
applied patches, the installed GRUB module/config actually used by bootc,
shim, and whether systemd-boot is installed/selected. **No claim is made
that shipping RHEL 10 will, or will not, start writing this variable.**
