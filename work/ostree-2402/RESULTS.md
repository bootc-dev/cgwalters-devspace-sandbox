## Design

The finalizing process opens a detached clone of the boot filesystem itself;
no fd is handed over from the hold process. When `/boot` lives on the
physical root (`/sysroot/boot/loader` is a symlink), the clone and every read
come from `/sysroot/boot`. Nothing is stacked on that path, so an expired
`boot.automount` over the generator's `/boot` bind mount can't take it away.
With a separate boot partition they come from `/boot`, as before.

The clone is made with `open_tree(OPEN_TREE_CLONE)` and
`mount_setattr(attr_clr=RDONLY)`, then reopened as a directory fd so that
`syncfs` and `FIFREEZE` work on it. If the kernel lacks the new mount API
(ENOSYS, or EPERM from an old seccomp filter), or the filesystem itself is
read-only, finalize falls back to the remount path ostree uses today.

`/boot` is still remounted read-write, because the path-based bootloader
backends (grub2-mkconfig, syslinux, uboot, zipl, aboot) write through `/boot`.
A failed remount is fatal only when there is no other writable boot fd, and it
is logged once (the "log-once" change).

The fd handover options were rejected because the systemd fd store only
returns fds to the unit that stored them; making the holder the finalizer
changes the shutdown ordering; and pidfd_getfd or SCM_RIGHTS would add IPC
and SELinux surface. Commit 4's message gives this reasoning.

`finalize-staged --hold` now opens `/boot` explicitly. In the previous run, a
build without that deadlocked in the VM. The hold stopped pinning `/boot`, the
automount expired, and stopping `boot.mount` stopped
`ostree-finalize-staged.service` (RequiresMountsFor=/boot). Finalize then
blocked in `statfs` → `autofs_expire_wait`.

## Verification

All VMs boot with SeaBIOS (q35 without pflash, so the ESP is unused), with
SELinux enforcing. The images are `quay.io/fedora/fedora-bootc:44` with ostree
built from source layered on (`scripts/Containerfile`). There is no fstab
workaround. The same-partition disks come from `bcvk to-disk --filesystem xfs`
(bcvk 0.22.0), which gives BIOS boot + ESP + xfs root with `/boot` on the
root. `scripts/idle-stage-reboot.sh` idles 190 s, checks
`unshare -m ostree admin status`, stages a redeploy with a marker karg, idles
190 s more, reboots, and prints what booted and the journal.

1. **Bug reproduces on stock Fedora ostree 2026.4** (previous run,
   `stock-repro-journal.txt`): `ostree[2141]: error: Remounting /boot read-write: Invalid argument`,
   and the staged deployment was dropped.
   `unshare -m ostree admin status` failed with
   `error: loading sysroot: fstatat(boot/loader): Operation not permitted`.

2. **Bug reproduces on unmodified main a4cb6781** (this run,
   `main-run.out`, same image recipe). After the automount expired:
   `unshare -m` status gave `fstatat(boot/loader): Operation not permitted`

3. **Fixed build, same partition: pass**, now including the log-once

   (In the logs, the freeze/thaw lines appear twice because upstream freezes
   at two call sites. `Copying /etc changes` and `Bootloader updated` appear
   twice because each is both sent to the journal and emitted as a message
   that the CLI prints. This change touches neither.)

4. **Separate /boot partition: pass** (`sepboot-run.out`). The disk has BIOS
   boot, an unused ESP, ext4 `/boot` and xfs root, installed with
   `bootc install to-filesystem` (`scripts/install-separate-boot.sh`). bootc
   wrote fstab `/boot auto ro`. There is no `boot.automount`.
   `unshare -m` status gave rc=0. Finalize logged `Finalizing staged deployment` …
   `Finalized deployment` … `Cleanup complete` with no error, and `.1` booted
   with `bz2402=sepboot` and `boot=UUID=…`, with `.0` as the rollback. Since
   that ext4 is mounted read-only, this should have taken the remount
   fallback, not the clone. That is inferred: the choice is logged only at
   debug level, and I didn't enable debug logging.

5. **Soft-reboot: pass** (`soft-reboot.out`, on the fixed same-partition
   VM). I staged a redeploy of the booted commit (same kernel and kargs),
   ran `ostree admin prepare-soft-reboot 0` (status showed
   `(staged) (soft-reboot)`), waited 190 s, and ran `systemctl soft-reboot`.
   Finalize ran at the soft-reboot as at a reboot: `boot.mount: Deactivated`,
   then `Writing the boot filesystem via /sysroot/boot; …`,
   `Finalized deployment`, `bootversion: boot.1.1`, `Cleanup complete`.
   Afterwards `.2` was booted with `.1` as the rollback, and uptime and
   `/proc/cmdline` carried over from before the soft-reboot. One
   observation: in the soft-rebooted userspace, `/boot` is the bind mount
   that `ostree-soft-reboot.c` makes, and `boot.automount` then logs
   `Path /boot is already a mount point, refusing start`. That comes from
   existing soft-reboot code, not this change. I didn't check whether stock
   does the same.

6. **New `bootc-integration` test** `privileged_verify_boot_path_not_required`.
   In a private mount namespace it puts a tmpfs over `/boot`, then runs
   `ostree admin status` and `kargs edit-in-place`, and checks the real

## Not verified / risks

- The fallback for kernels without `open_tree`/`mount_setattr` was not run on
  such a kernel. The separate-/boot run covers the remount path only through
  the read-only-filesystem case, and only by inference.
- Path-based bootloader backends (grub2-mkconfig and others) still need `/boot`
  to be writable through its path. These BLS-only Fedora images don't use
  them, so a grub2-mkconfig system with this automount layout was not tested.
- These runs didn't check SELinux labels. The previous run found BLS entries
  labeled `boot_t` with nothing for `restorecon -n` to change under
  `/boot/loader*`.
- Only Fedora 44 (kernel 7.2, systemd 259) was tested; centos-bootc
  stream10 was not run with the fix.
