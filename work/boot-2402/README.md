# boot-2402: how /boot is mounted, and whether updates survive its automount

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

This is a VM harness for [bootc#2402](https://github.com/bootc-dev/bootc/issues/2402).
On ostree systems, systemd-gpt-auto-generator can put a `boot.automount` with
`TimeoutIdleSec=120` over `/boot`. Once that idles out, updates fail to finalize.
The harness installs a host, waits for `/boot` to idle out, stages an update,
waits again, reboots, and checks whether the new deployment booted. It records
how `/boot` was mounted at each step. Results and evidence are in
[RESULTS.md](RESULTS.md).

## Requirements

You need `/dev/kvm`, `qemu-kvm` (or set `QEMU=qemu-system-x86_64`), OVMF
(`edk2-ovmf`), `qemu-img`, `xorriso`, `mkisofs`, `ssh`, `curl` and Node.js 18
or newer. It doesn't need root, host podman or bcvk. Everything that needs root
(podman, `bootc install`, partitioning) runs inside a Fedora Cloud "builder" VM
that the harness boots, so it works as is on the devspace RHEL 10 runners.
State (downloads, disks, run logs, about 300 GB at most) goes to
`$B2402_STATE`, which defaults to `/var/tmp/b2402`. If
`/etc/egress-proxy/ca.pem` exists (the agent sandbox's TLS-intercepting proxy),
the harness adds it to the trust store of the builder and of the Silverblue
guests. Set `B2402_EXTRA_CA` to use a different file.

## Running it

```console
cd work/boot-2402
node harness.mjs fetch                  # Fedora 45 Cloud qcow2 (builder) + Silverblue 45 ISO
node harness.mjs build-bootc            # fedora-bootc:45 and centos-bootc:stream10, stock and ostree PR 3690, all layouts
node harness.mjs install-silverblue     # Silverblue 45 from the ISO, one install per layout
node harness.mjs fetch-rpms             # Fedora ostree RPMs with PR 3690, for the Silverblue PR runs
node harness.mjs matrix --jobs 16       # every built disk; BIOS too where the layout lists it
node harness.mjs silverblue-pr          # Silverblue disks again, with ostree PR 3690 applied
node harness.mjs report                 # Markdown table of all results
```

Each step skips work that is already done; pass `--force` to redo it. Use
`--image`, `--variant` and `--layout` to build a subset, and `--filter REGEX`
to run a subset. To run a single disk, use
`node harness.mjs run fedora-bootc-45--stock--root --firmware bios`. Add
`--no-idle` for a control run that touches `/boot` and updates straight away.
`node harness.mjs --help` lists the image and layout names.

Each run leaves this in `$B2402_STATE/runs/<id>/`:

- `evidence.txt`: every command and its output. That covers versions,
  `lsblk`, `/etc/fstab`, `findmnt`, the `/boot` and `/efi` units under
  `/run/systemd/generator*`, `systemctl status boot.mount boot.automount ...`,
  the staging output, and the previous boot's `ostree-finalize-staged` journal.
- `serial.log`: the full console, including shutdown.
- `result.json`: the summary that `report` reads.

## What a run does

The flow follows Fedora openQA's ostree tests (`rpmostree_rebase.pm`,
`rpmostree_overlay.pm` in os-autoinst-distri-fedora): stage, `systemctl
reboot`, then check which deployment booted. openQA has no bootc tests and
never leaves a system idle, so this harness adds the idle waits.

1. Boot the disk in a fresh qcow2 overlay, UEFI (OVMF) or BIOS (SeaBIOS), and
   record how `/boot` is mounted. The probes only read `/proc` and unit
   state. Nothing touches `/boot` itself, which would trigger the automount.
2. If `boot.automount` is active, wait up to 240 s for `boot.mount` to go
   inactive, which is the idle-out.
3. Stage the update. bootc images use `bootc switch --transport oci-archive`
   to a derived image that adds `/usr/share/b2402/next`. Silverblue uses
   `rpm-ostree upgrade` from the GA install to the current Fedora 45, and then
   `rpm-ostree kargs --append`. If staging fails, the harness records the
   error, runs `ls /boot` and stages again, so finalize still gets tested.
4. Wait for an idle-out again, reboot, and check that the new deployment
   booted: the marker file, a changed booted checksum, or the karg.

## How the disks are made

- **bootc**, in the builder VM:
  - `root` layouts use `bootc install to-disk --filesystem xfs`, which gives
    a BIOS boot partition, an ESP and root, with `/boot` on root.
  - `part` and `xbootldr` layouts partition the disk with `sfdisk`: BIOS boot,
    ESP, an ext4 `/boot` (generic Linux type, or the XBOOTLDR type) and an xfs
    root. They install with `bootc install to-filesystem`.
  - After installing, the harness rewrites the deployment's `/etc/fstab`
    entries for `/boot`, `/boot/efi` and `/efi` to match the layout.
  - `efidir` layouts install from a derived image with `RUN mkdir /efi`.
  - `pr3690` disks install from a derived image that carries ostree rebuilt
    from the distribution's own source RPM, with the commits of
    [ostree#3690](https://github.com/ostreedev/ostree/pull/3690) added as
    patches.
- **Silverblue**: Anaconda installs from the ISO, using direct kernel boot and
  a kickstart on an `OEMDRV` volume.
  - `sb-default` uses `autopart --type=btrfs`, which gives an ESP at
    `/boot/efi`, an ext4 `/boot` and btrfs root, like the default GUI
    install.
  - The other `sb-` layouts drop fstab lines in `%post`, or put `/boot` on an
    xfs root.
  - For the PR runs, `rpm-ostree override replace` installs the patched
    Fedora RPMs as a setup step, with `/boot` freshly mounted.
