# bootc composefs backend and bootc#2402

> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

Summary: with the composefs backend, an expiring `boot.automount` doesn't drop
a staged deployment in any of the three layouts tested (UEFI with a DPS root,
and BIOS with and without a simulated automount). `hold_boot()` is what
prevents it. With the hold stopped after staging, the same runs drop the
staged deployment, and finalize fails with `Opening /boot: Host is down`. So
PR #30's fd approach wasn't ported, and there are no patches.

## Setup

bootc-dev/bootc main at 7cde7bbe (1.17.4), with bootc#2602's two commits
cherry-picked (8a424397 and e2745d19 locally), built with
`just variant=composefs base=quay.io/fedora/fedora-bootc:44 build` (systemd
259 in the guest). `scripts/Containerfile` layers each test image on top:
`base` and `upgrade` markers, with DPS kept (`dps=true`) for UEFI and turned
off for BIOS. Disks come from `bcvk to-disk --disk-size 20G
--composefs-backend --bootloader grub --filesystem ext4 --format qcow2`
(bcvk 0.22.0; the runner needed a virtiofsd binary, taken from CentOS Stream
10, via `VIRTIOFSD_BIN`). They have a same-partition layout: BIOS boot, ESP
and root, with no separate /boot. `scripts/vm.sh` boots them with SeaBIOS,
or with OVMF when `FIRMWARE=uefi`. `scripts/idle-stage-reboot.sh` copies the
upgrade image in as an oci-archive, idles 190 s, stages it with
`bootc switch --transport oci-archive`, idles 190 s, reboots, and reports
the booted marker, `bootc status` and the previous boot's journal. Each run
uses a fresh qcow2 overlay of the installed disk.

## Why hold_boot() prevents it

Staging always mounts the ESP, even after it has expired. bootc re-execs
itself under `unshare -m --propagation=slave` (`ensure_self_unshared_mount_namespace`
in `crates/lib/src/cli.rs`). From that slave namespace, its open of `/boot`
reaches systemd as an automount request ("triggered by … (bootc)"), and the
mount propagates in. (A plain `unshare -m`, which is private, gets EPERM
instead; that's the symptom PR #31 saw.) Staging then starts
`bootc-finalize-staged-hold.service`. Its `hold_boot()`
(`crates/lib/src/bootc_composefs/finalize.rs`) opens `/boot` in the root
namespace and keeps the fd. autofs treats a mount with an open fd as busy, so
`boot.mount` stays mounted until shutdown: 190 s after staging, well past
the 120 s timeout, it was still mounted, with the hold's fd 11 pointing at
it. The hold unit is ordered so it stops only after
`bootc-finalize-staged.service`'s ExecStop has run, and systemd unmounts
/boot only after that.

Without the hold, the expiry happens, and at shutdown systemd refuses the
new automount request with EHOSTDOWN. The first thing finalize touches is
`Dir::open_ambient_dir("/boot")` at the top of `get_boot_dir_for_grub()`
(`crates/lib/src/store/mod.rs`), so storage initialization fails and
finalize exits 1. bootc's composefs code is otherwise less exposed to
#2402 than ostree: on a same-partition layout `get_boot_dir_for_grub()` sees
the vfat ESP on /boot and picks `/sysroot/boot`; it never remounts `/boot`.
The ESP itself is mounted by device into a temporary mount
(`mount_esp_writable()`), not through /boot.

## Remaining risk and what wasn't done

The protection depends on the hold process staying alive from staging
until shutdown. If it dies (OOM kill, a manual stop, a crash), the controls
show the staged deployment is silently dropped, as in #2402. A cheap
hardening, not written here, would be for `get_boot_dir_for_grub()` to
tolerate a failed open of `/boot` when `/sysroot/boot` holds GRUB's
configuration, since on a same-partition layout /boot isn't needed at all.
PR #30's fd approach would be the fuller fix. Neither was implemented,
because the task asked for a fix only if a real case dropped the deployment.

Not tested: a separate /boot partition, systemd-boot or UKI boot types,
soft-reboot, and centos-bootc stream10. cargo test and clippy weren't run,
since no bootc code changed.

## Earlier findings (PR #31)

1. **On BIOS there is no `boot.automount` with the composefs backend**
   (`stock-main-bios.out`). systemd-gpt-auto-generator logs
   `Neither root nor /usr/ file system are on a (single) block device` and
   `Skipping automatic GPT dissection logic`. bootc's initramfs
   (`gpt_workaround()` in `crates/initramfs/src/lib.rs`) writes
   `/run/systemd/volatile-root` only when `/dev/gpt-auto-root` exists, that
   is, for a DPS root, which needs UEFI. With the same Fedora 44 base, the
   ostree backend does get `boot.automount`, because ostree-prepare-root
   always writes volatile-root (`contrast-ostree-bios.out`).
2. **Stock main can't stage at all on BIOS**: `Finding ESP used for booting:
   Reading LoaderDevicePartUUID-…: SystemNotUEFI`, tracked upstream as
   bootc#2605 with a fix in bootc#2602, which these runs include.
3. The dev image's `discoverable-partitions = true` gives an unbootable BIOS
   install, since DPS root discovery needs UEFI loader variables.
4. A composefs pull of an image loaded from a docker-archive
   (containers-storage transport) fails with `Invalid splitstream content
   type`, and taints later pulls; the oci-archive transport works. Probably
   related to bootc#1703, and unrelated to #2402.

PR #31's incomplete `base-bios-*.out` files are replaced by the outputs
above.
