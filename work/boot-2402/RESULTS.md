## Source answer to the fstab question (systemd v257 to v262)

- gpt-auto-generator `process_loader_partitions()` (v262 gpt-auto-generator.c:1089, v257:730) calls `fstab_has_mount_point_prefix_strv(STRV_MAKE("/boot", "/efi"))`. Any fstab entry at or under `/boot` or `/efi` (including `/boot/efi` alone) suppresses both the ESP and the XBOOTLDR automounts.
- `add_partition_esp` (v262:671-700) puts the ESP at `/boot` whenever there is no XBOOTLDR and `/boot` is an empty, unmounted directory. An ostree deployment's `/boot` is exactly that. It falls back to `/efi` only if `/boot` is busy, so **adding `/efi` to the image does not help** (confirmed below).
- On BIOS boots the LoaderDevicePartUUID check is skipped (v262:1098), so an unused ESP is still automounted.
- The idle timeout is hardcoded at 120 s (`LOADER_PARTITION_IDLE_USEC`) and is not configurable.
- gpt-auto writes to `generator.late`, so ostree's `boot.mount` (in `generator`) wins the unit name. Nothing competes with `boot.automount`, which then drives ostree's bind mount.
- ostree's generator skips its `boot.mount` for an exact `/boot` fstab entry only from v2026.5. The skip doesn't matter for 2026.4 with a separate `/boot`, because that path never generates the bind mount.
- ostree 62109dca (v2026.3) makes gpt-auto work on composefs roots, which is what exposed this.

## Second run (2026-11-09, fresh runner, all disks rebuilt)

Versions: fedora-bootc:44 has systemd 259.10, ostree 2026.4, bootc 1.17.1. centos-bootc:stream10 has systemd 257-35.el10, ostree 2026.4, bootc 1.17.1. PR 3690 head 00cbd2f9. The gpt-auto logic (fstab prefix check, BIOS skips the LoaderDevicePartUUID check, 120 s idle) is the same in v257 (gpt-auto-generator.c:730,738,748), v259 (:1015,1023,1033) and v262.

- **fedora-bootc-44** behaves exactly like 45: stock `root` and `root-efidir` fail finalize after the idle-out (UEFI and BIOS), `root-fstab-esp` and every `/boot` fstab layout survive, and PR 3690 survives all `root` layouts.
- **CentOS Stream 10**: its grub does not set `LoaderDevicePartUUID`, so on UEFI gpt-auto creates no automount and stock ostree survives every UEFI layout. On **BIOS** the check is skipped: stock `root` gets `boot.automount`, idles out at 159 s and fails finalize with `Remounting /boot read-write: Invalid argument`; PR 3690 survives. The no-fstab separate-`/boot` layouts fail at staging (`Initializing storage: Remounting /boot read-write: Invalid argument`) because nothing mounts `/boot`.
- **Silverblue `sb-noboot-nofstab`** (`/boot` on xfs root, Anaconda's `/boot/efi` line removed) reproduces the bug with `rpm-ostree upgrade`: automount idles out at 156 s, finalize fails with the same error. Default Silverblue is unaffected.
- **ext4 XBOOTLDR without fstab (Fedora)** does not boot: gpt-auto doesn't probe the fstype, `partition_pick_mount_options()` adds `fmask=0177,dmask=0077`, ext4 rejects it, and the kernel logs `FAT-fs (vda3): bogus number of reserved sectors`. Unsupported layout, not this bug.
- Harness fixes: `parseProbe` now finds `Id=` anywhere (systemd 257 orders properties differently); a `LoaderDevicePartUUID` probe was added; the Silverblue PR 3690 override now runs before the measured steps. The first Silverblue PR runs applied the override after the upgrade, so their results are invalid; the re-run was in progress when the session ended.

## What this shows

- **The bug reproduces** on a stock `bootc install to-disk` of fedora-bootc:45, on both UEFI and BIOS. Staging after the idle-out works (bootc 1.17.1 includes bootc#2411). Finalize at shutdown fails, though, and the update is silently dropped. Staging re-mounts `/boot` and the hold service keeps it mounted, so it did not idle out again after staging. The control run without an idle-out before staging succeeds.
- **ostree PR 3690 fixes every `/boot`-on-root layout we tested**, on UEFI and BIOS.
- **Default Silverblue (Anaconda) is not affected**: its fstab has `/boot` and `/boot/efi` entries, so gpt-auto generates no automount. That matches the source.
- Removing Anaconda's `/boot` fstab line breaks a separate-`/boot` system regardless of this bug.
