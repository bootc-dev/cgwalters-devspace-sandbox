## Prototype

`patches/` is `git format-patch` output against ostreedev/ostree main a4cb6781. Patches 0001-0004 are PR 3690 as it stands. Patches 0005-0006 are the spike:

- 0005 adds `src/libostree/ostree-bootfs.c`. On a booted system with a separate `/boot`, it attempts to open the boot filesystem as a detached mount. It first tries `open_tree(OPEN_TREE_CLONE)` of the `/boot` mount, opened `O_PATH` so an automount is not triggered. If that mount isn't there, it uses `fsopen`/`fsconfig`/`fsmount` on the fstab device or `/dev/disk/by-designator/xbootldr`. It falls back to the path on **any** detached-open failure, or for an unprivileged process. To make it writable, it uses `fspick` plus a reconfigure to `rw`, not a remount of `/boot`. When `/boot` is on root, PR 3690 already opens `/sysroot/boot`.
- 0006 changes the finalize units from `RequiresMountsFor=/boot` to `WantsMountsFor=/boot`. An expiring automount then no longer stops the unit, which would finalize early. This makes the `/boot` hold from PR 3690 unnecessary.

The branch was not pushed to cgwalters-forge/ostree. Nothing went upstream.

## Source comparison with PR 3690

**Systemd and mount lifetime.** PR 3690 opens `/sysroot/boot` on root and holds
the matching `/boot` bind mount so that `RequiresMountsFor=` does not stop
finalize early. For separate `/boot` it keeps the existing path-based mount.
0005 instead holds a private clone or new mount; 0006 weakens the dependency to
`WantsMountsFor=` and removes the path hold. Ordering remains, but requiring a
mounted `/boot` no longer does. A private mount is invisible in systemd's mount
tree, yet its superblock state is shared: `mount_boot_device()` first requests
read-write, conflicting with bootc's later read-only mount. The log above shows
this can happen just from the hold service opening the filesystem, not only
from a deployment write. Reconfiguring the superblock also affects other mounts.
This requires a mount-policy/lifetime design, not just suppressing mount errors.

**SELinux.** PR 3690 retains the existing filesystem and its mount options.
The detached clone inherits the source mount, but the fresh-mount path only
passes `source` and possibly `ro`; it ignores fstab's `context=`, `fscontext=`,
and other filesystem-specific options. Existing inode labels and ostree's
explicit `/boot` creation-label lookup remain relevant, but cannot compensate
for changed mount policy. The ext4 `boot_t` entries and zero AVCs in the linked
log do not validate vfat/XBOOTLDR or context mounts.

**Durability.** Both variants retain ostree's bootloader swap and filesystem
sync/freeze protocol (`ostree-sysroot-deploy.c`, `full_sync()` and
`fsfreeze_thaw_cycle()`). A usable directory fd pins the filesystem and supports
those operations; the original `O_PATH` fd did not. Closing the last mount fd
is not a substitute for explicitly checking synchronization errors. Reboot
tests, including the successful freeze/thaw in #48, are not power-loss tests.
The unchanged GRUB backend writes `boot/loader.N/grub.cfg` through
`sysroot->path`, not `boot_fd`. Making the detached clone writable does not
clear the original mount's read-only flag, so that write can still fail with
`EROFS`. Backends that invoke external bootloader tools also need a path audit;
these patches do not establish that every bootloader write is independent of
`/boot`. The pilot images used `sysroot.bootloader=none`, not that GRUB path.

**Build and old-kernel fallback.** The review question about `HAVE_OPEN_TREE`
is resolved by the pinned upstream
[`configure.ac`](https://github.com/ostreedev/ostree/blob/a4cb6781b92da59107a6e6c44bee77898054cc25/configure.ac#L128-L133):
`AC_CHECK_FUNCS([open_tree])` defines that macro when available. No missing
definition fix is needed. However, that probe alone does not check the other
libc functions and header types used here. The prototype needs the new mount
API (Linux 5.2) and `mount_setattr` (5.12), plus compatible libc headers/wrappers.
A runtime failure falls back to `/boot`, which loses detached operation; it
does not restore the path hold removed by 0006. Old-kernel/fallback behavior
therefore needs testing before treating 0006 as safe. PR 3690 adds no such API
requirement.

**Interactive commands.** The same sysroot-open path is used by `ostree admin`,
not just shutdown finalize. On-root access uses `/sysroot/boot` in both variants.
On separate `/boot`, privileged commands in 0005 try the detached path even for
reads, while unprivileged commands trigger the ordinary mount path. A successful
`status` or `kargs edit-in-place` alone is insufficient: verify subsequent
systemd mounts, the resulting entries, and reboot. The original harness runs
these commands in the host namespace; a separate private-namespace interactive
case is still needed. No bootc composefs-backend changes were made.
