# boot-2402: ext4 loop-mount EUCLEAN investigation
> This text was generated by an LLM ([how cgwalters uses LLMs](https://github.com/cgwalters/cgwalters#llms)). cgwalters has not reviewed it yet.

1. Reproduced the exact three commands in Fedora 45 with kernel `7.2.13-300.fc45` and e2fsprogs `1.47.4-2.fc45`: mount exits 32 with EUCLEAN.
2. Kernel diagnostic: `EXT4-fs (loop0): orphan file too big: 681984`; inode 12 really has that size, exceeding the kernel's 512 KiB limit at 1 KiB blocks.
3. Both 7.2.13 and previous-series Fedora kernel `7.1.13-200.fc44` fail at 1 KiB and pass at 4 KiB with the same Fedora 45 userspace: not a new 7.2-only regression.
4. e2fsprogs commit `6f03c698ef53` changes default orphan sizing; no ostree command or PR binary is needed to reproduce (full main kola test not run).
5. The attached minimal patch specifies `-E orphan_file_size=512K`, preserving image capacity and block-size coverage; patched mounts pass at 1/4 KiB on both kernels.

## Cause: incompatible orphan-file sizing, not ostree

The evidence identifies the failing check, not merely a correlation with block
size. In [`ext4_init_orphan_info()` in Linux v7.2](https://github.com/torvalds/linux/blob/v7.2/fs/ext4/orphan.c),
`EXT4_MAX_ORPHAN_FILE_BLOCKS` is 512. An inode size greater than
`512 << inode->i_blkbits` logs the exact message above and returns
`-EFSCORRUPTED` (`EUCLEAN`). This artificial limit bounds pinned orphan-file
memory. **681984 = 666 × 1024 > 512 × 1024 = 524288**.
The [v7.1 source](https://github.com/torvalds/linux/blob/v7.1/fs/ext4/orphan.c)
already has this check; the failing control confirms it is not introduced by
the 7.1-to-7.2 upgrade.

Relevant kernel history predates both versions:

- [`0a6ce20c1564`, ext4: verify orphan file size is not too big](https://github.com/torvalds/linux/commit/0a6ce20c156442a4ce2a404747bb0fb05d54eeb3)
  introduced an 8 MiB safety cap.
- [`7c11c56eb32e`, ext4: align max orphan file size with e2fsprogs limit](https://github.com/torvalds/linux/commit/7c11c56eb32eae96893eebafdbe3decadefe88ad)
  replaced that with 512 filesystem blocks, describing the older e2fsprogs
  default of 32–512 blocks. This reduces the cap to 512 KiB at 1 KiB blocks.

The relevant **userspace change** is
[`6f03c698ef53`, libext2fs: fix orphan file size > kernel limit with large blocksize](https://github.com/tytso/e2fsprogs/commit/6f03c698ef53bb9d0cd42c9bd0b68e8ce72f8345),
present in the [v1.47.4 source](https://github.com/tytso/e2fsprogs/blob/v1.47.4/lib/ext2fs/orphan.c).
It fixes the large-block case by adding an 8 MiB creation cap, but also changes
default sizing from `num_blocks / 4096` to `num_blocks / fs->blocksize` in the
intermediate-size branch. [`ext2fs.h`](https://github.com/tytso/e2fsprogs/blob/v1.47.4/lib/ext2fs/ext2fs.h)
defines `EXT4_DEFAULT_ORPHAN_FILE_SIZE` as `2 << 20` and
`EXT4_MAX_ORPHAN_FILE_SIZE` as `8 << 20`. The branch compares **filesystem block
count** with 128 × 1024 and 2 × 1024 × 1024, then divides block count by block
size. With no bigalloc cluster rounding:

```text
1 KiB: floor(699137405 / 1024) = 682748 blocks
       floor(682748 / 1024) = 666 orphan blocks = 681984 bytes
4 KiB: floor(699137405 / 4096) = 170687 blocks
       floor(170687 / 4096) = 41 orphan blocks = 167936 bytes
```

These calculations exactly match debugfs. The old
[v1.47.3 formula](https://github.com/tytso/e2fsprogs/blob/v1.47.3/lib/ext2fs/orphan.c)
would select `floor(682748 / 4096) = 166` blocks for this 1 KiB image, below the
kernel cap. That is a **source comparison**, not a separately executed 1.47.3
binary control. The [1.47.4 release notes](https://github.com/tytso/e2fsprogs/blob/v1.47.4/doc/RelNotes/v1.47.4.txt)
mention the fix for orphan files exceeding the kernel limit at 64 KiB blocks;
they do not warn of this small-block incompatibility. The VM's default mkfs
enables `orphan_file`, as confirmed by dumpe2fs. The reproducer establishes a
kernel/userspace default incompatibility on freshly created images, not random
storage corruption or evidence of a new 7.2 ext4 regression.

No exhaustive ext4/VFS diff audit or kernel bisect was necessary after matching
the exact check and reproducing it on both kernel series. A GitHub whole-kernel
compare caps its changed-file list at 300; absence of ext4 from that list would
**not** establish absence of ext4 changes. No such inference is used here.

## Minimal test patch

[auto-prune-orphan-file.patch](auto-prune-orphan-file.patch) applies to upstream
main at `896d5225cd670484d57351b26cf6e561178f9938`. It changes only mkfs options:

```diff
-    mkfs.ext4 -b ${block_size} ${bootimg}
+    # e2fsprogs 1.47.4 can default to an orphan file larger than the
+    # kernel's 512-block limit on 1 KiB filesystems. Keep it within that limit.
+    mkfs.ext4 -b ${block_size} -E orphan_file_size=512K ${bootimg}
```

This preserves the existing block size, all subsequent `dd`/free-block
calculations, the five-pair image byte capacity and ext4 reserved-space behavior.
512 KiB occupies at most 512 filesystem blocks at ext4's minimum 1 KiB block
size, and 128 blocks at 4 KiB. The test does not depend on default orphan-file
sizing. This is a test workaround, not a proposed kernel or e2fsprogs repair.

Forcing 4 KiB also bypasses the error at this image size, but would require
re-reading `block_size=$(stat --file-system /boot -c '%s')` after mounting the
replacement and would remove 1 KiB coverage. Avoiding the loop mount is a larger
change to the test's controlled filesystem sizing. Explicit orphan sizing is
the smaller, targeted workaround; it does not globally disable `orphan_file`.

### Patch validation

Ran the following as root inside the disposable Fedora 45 VM on **each** of
`7.1.13-200.fc44` (21:27:14 UTC) and `7.2.13-300.fc45` (21:27:35 UTC), with
e2fsprogs unchanged. Both command batches exited **0**:

```sh
set -e
for bs in 1024 4096; do
    truncate -s 699137405 /var/tmp/boot.img
    mkfs.ext4 -q -b "$bs" -E orphan_file_size=512K /var/tmp/boot.img
    debugfs -R 'stat <12>' /var/tmp/boot.img
    mount -o loop /var/tmp/boot.img /var/mnt
    test "$(stat -f -c %s /var/mnt)" = "$bs"
    umount /var/mnt; rm /var/tmp/boot.img
done
```

All four mounts pass. Debugfs reports size **524288** with extents `(0-511)`
at 1 KiB and `(0-127)` at 4 KiB. `git apply --check` passes against the pinned
upstream file, and `bash -n` passes after applying the patch in a temporary
upstream-shaped directory. Full auto-prune ENOSPC/pruning assertions remain
**unvalidated**; run the patched kola test on main and PR 3690 before upstreaming.
