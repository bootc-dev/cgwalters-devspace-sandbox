## Findings so far

1. **On BIOS there is no `boot.automount` with the composefs backend**
   (`stock-main-bios.out`). systemd-gpt-auto-generator logs
   `Neither root nor /usr/ file system are on a (single) block device` and
   `Skipping automatic GPT dissection logic`. `/` is a composefs overlay, and
   bootc's initramfs (`gpt_workaround()` in `crates/initramfs/src/lib.rs`)
   writes `/run/systemd/volatile-root` only when `/dev/gpt-auto-root` exists,
   that is, when root was found through DPS, which needs UEFI. A BIOS install
   has `root=UUID=` and no volatile-root. With the same Fedora 44 base, the
   ostree backend does get `boot.automount` (timeout=120), because
   ostree-prepare-root always writes volatile-root (`contrast-ostree-bios.out`).
   So #2402's trigger doesn't occur for composefs on BIOS today.
2. **Stock main can't stage at all on BIOS.** `bootc status` and `bootc switch`
   fail with `Finding ESP used for booting: Reading LoaderDevicePartUUID-…:
   SystemNotUEFI`. Upstream already tracks this as bootc#2605, with an open fix
   in bootc#2602. The remaining runs use main with #2602 cherry-picked.
3. The dev image's `discoverable-partitions = true` (Fedora ≥ 43, set in
   `contrib/packaging/install-rpm-and-setup`) gives an unbootable BIOS install,
   since DPS root discovery needs UEFI loader variables.
   `scripts/Containerfile` turns it off for these tests.
4. A composefs pull of an image that was `podman load`ed from a docker-archive
   (containers-storage transport) fails with `Invalid splitstream content type`,
   and later pulls on that system fail the same way, even from oci-archive. On a
   fresh disk the oci-archive transport stages fine. This is probably related to
   bootc#1703 and is unrelated to #2402.
5. With an automount simulated by hand (volatile-root created, then
   `boot.automount` started), after 190 s idle `unshare -m ls /boot` gives
   `Operation not permitted`, the same symptom as the ostree bug. An earlier
   attempt didn't get as far as staging, because of finding 4.
